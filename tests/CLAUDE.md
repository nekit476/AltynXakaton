# tests/ — модуль тестов

Один инструмент (pytest), один отчёт (Allure). Структура повторяет модули кода.

| Папка | Владелец | Что |
|---|---|---|
| `core/` | A | Платформа: пользователи, настройки, служебные URL, вход, права |
| `domain/<app>/` | B | Сервисы, селекторы, формы, задачи Celery |
| `web/` | C | Страницы и HTMX-фрагменты |
| `test_architecture.py` | A | Сторож границ модулей |
| `authz/` | A | Матрица прав «роль × URL × свой/чужой × GET/POST/HTMX» (#24) |
| `e2e/` | A + C | Playwright, маркер `e2e` (#28, #67) |
| `load/` | A | Сценарии k6 (#42) |
| `conftest.py` | A | Общие фикстуры. Фикстуры одного модуля — в его `conftest.py` |

## Как писать тест

- Класс на смысловую группу. В докстроке класса — нумерованный перечень тестов.
- `@allure.feature` / `@allure.story` на классе, `@allure.title` над каждым тестом.
- Внутри теста три блока через пустую строку: подготовка, действие, проверка. Подготовка длиннее трёх строк уходит в фикстуру.
- Параметризация вместо копий: данные выносятся в константу модуля, у каждого `pytest.param` есть `id` по-английски.
- `pytest.raises(..., match=...)` — всегда с `match`.
- Проверяется не только результат, но и причина: тип ошибки, сработавшая политика, упавший компонент.
- БД — только с `@pytest.mark.django_db`. Без этой метки тест падает при обращении к базе, и это тоже проверка.
- Тест, который зеленеет всегда, сразу на подозрении. Сторож без нарушений проверяется на подложенном примере.

## Запуск

```bash
uv run poe test                 # всё
uv run poe test tests/core      # один модуль
uv run poe test -k health       # по имени
uv run pytest --alluredir allure-results   # с отчётом Allure
```

Тестам нужна PostgreSQL из `DATABASE_URL`. pytest-django создаёт рядом базу `test_<имя>`, у каждого участника свою. Redis тестам не нужен.
