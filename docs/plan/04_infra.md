# 04. Инфраструктура: расчёт VPS и деплой

## 1. Из какой нагрузки считаем

| Параметр | Значение | Откуда |
|---|---|---|
| Студентов | ~10 тыс. очных (2025). Закладываем **15 тыс. пользователей** с преподавателями и запасом. | [statbase.ru](https://statbase.ru/data/gubkin-russian-state-university-of-oil-and-gas-russian-federation-number-of-students-by-university/) |
| Групп | ~400 | 10 тыс. / ~25 |
| Одновременно активных в пик | **3 тыс.** (20 %) | Утро перед первой парой, выкладка оценок |
| Запросов на активного | 1 раз в 10 с: переходы и HTMX-фрагменты + опрос бейджа раз в 60 с | Оценка |
| Устойчивая нагрузка | **300 RPS** (из них ~50 RPS — опрос бейджа уведомлений) | 3000 / 10 + 3000 / 60 |
| Пики | **500 RPS** на 1–2 минуты | Выкладка оценок, «все открыли расписание после переноса» |
| Сдача ДЗ в последний час | 500 × 5 МБ за 5 мин ≈ 8 МБ/с ≈ **70 Мбит/с** | Худший случай. Канал 1 Гбит/с выдерживает. |
| Цели (SLO) | p95 < 300 мс на страницы и фрагменты, < 1 с на загрузку до 10 МБ, ошибок < 0,5 % | Для k6 |

Почему хватит одного сервера:
- **Расписание кэшируется по группам.** Кэш фрагментов (`{% cache %}`) и сервисов по ключу `group_id + неделя`, групп ~400 — почти стопроцентное попадание.
- **Бейдж уведомлений** берёт счётчик из Redis, а не `COUNT(*)` из БД.
- **HTMX-фрагменты лёгкие**: обычно это кусок в 1–5 КБ, а не вся страница.

## 2. Бюджет памяти по контейнерам

| Контейнер | Лимит RAM | Обоснование |
|---|---|---|
| caddy | 128 МБ | Обычно 30–60 МБ. Буфер загрузок держится на диске, не в RAM. |
| web (gunicorn gthread, 6 воркеров × 4 потока) | 1,5 ГБ | ~130 МБ × 6 ≈ 800 МБ + **пик argon2**: 24 одновременных хеша × 19 МиБ ≈ 460 МБ |
| worker (Celery, concurrency 2) | 768 МБ | WeasyPrint на одну справку 100–250 МБ |
| beat | 128 МБ | Только планировщик |
| postgres | 2 ГБ | `shared_buffers = 1GB`, `work_mem = 8MB`, `max_connections = 100`. Остальное — кэш ОС. |
| redis | 384 МБ | `maxmemory 256mb`, AOF включён (очередь Celery переживёт перезапуск) |
| **Итого приложение** | **~4,9 ГБ** | |
| prometheus + grafana + exporters | 640 МБ | Профиль `monitoring` на время нагрузочных тестов |
| ОС + Docker | ~600 МБ | Ubuntu 24.04 minimal |
| **Итого с мониторингом** | **~6,1 ГБ** | |
| Свободно на 8 ГБ | ~1,9 ГБ | Кэш страниц PostgreSQL и файлов, всплески. ClamAV (+1,2 ГБ) влезет впритык, при нём мониторинг держать выключенным. |

**На 4 ГБ не берём:** под нагрузочным тестом начнутся swap и OOM-killer.
Staging во время разработки живёт на том же VPS отдельным compose-проектом с урезанными лимитами (2 воркера, ~1,5 ГБ). Перед финальным нагрузочным тестом его останавливаем.

## 3. CPU и диск

| Ресурс | Нужно | Обоснование |
|---|---|---|
| vCPU | **4** | Рендер шаблонов в Django упирается в CPU: каждый процесс gunicorn ограничен GIL, поэтому 6 процессов на 4 ядра, а потоки закрывают ожидание БД и Redis. Число воркеров уточняем по `stress`-прогону k6. |
| Диск | **80 ГБ NVMe** | ОС 10, образы 3, БД с данными на 10 тыс. студентов < 5, файлы ДЗ ≤ 20, бэкапы 7 × ~0,5, буфер загрузок Caddy, логи с ротацией |
| Сеть | 1 Гбит/с без жёсткого лимита трафика | Загрузки ДЗ и нагрузочные тесты |

## 5. Настройки, которые нельзя забыть

- **gunicorn:** `--worker-class gthread --workers 6 --threads 4 --timeout 30 --max-requests 5000 --max-requests-jitter 500`. Последние два параметра — страховка от утечек памяти.
- **Caddy:**
  - `request_body { max_size 25MB }`;
  - **буферизация тела запроса перед проксированием** (опция `request_buffers` у `reverse_proxy`), чтобы медленный мобильный аплоад не держал поток gunicorn;
  - `intercept` для `X-Accel-Redirect` — отдача файлов ДЗ;
  - `encode zstd gzip`.
- **Django:**
  - `CONN_MAX_AGE=60` и `CONN_HEALTH_CHECKS=True`. Постоянные соединения: 6 × 4 = до 24 соединений от `web`, это меньше `max_connections`.
  - `ATOMIC_REQUESTS=False` и явные `transaction.atomic` в сервисах, чтобы контролировать `on_commit`.
- **Redis:** кэш с TTL (`volatile-lru`), сессии хранятся в БД с кэшем в Redis, поэтому вытеснение не разлогинивает. `appendonly yes` для очереди Celery.
- **PostgreSQL:** `shared_buffers=1GB`, `effective_cache_size=4GB`, `random_page_cost=1.1`, `log_min_duration_statement=200ms`, чтобы ловить медленные запросы на нагрузке.

## 6. Деплой

```
git push main → CI: тесты → сборка ОДНОГО образа (стадия tailwind → python → collectstatic)
             → ghcr.io/<org>/dekanat:<sha>
             → SSH на VPS под deploy → infra/scripts/deploy.sh <sha>
                 1. docker compose pull
                 2. docker compose run --rm web python manage.py migrate --noinput
                 3. docker compose up -d --remove-orphans      (web, worker, beat — один образ)
                 4. curl -f https://<домен>/ready/              (иначе откат на предыдущий sha)
             → Playwright smoke против прода
```

- Прод: `dekanat.<домен>`. Staging: `staging.<домен>`, Caddy выпускает оба сертификата.
- Откат: `deploy.sh <предыдущий_sha>`. Миграции пишем обратимыми, перед релизом проверяем откат на копии.
- `harden-server.sh` идемпотентный: пользователь, SSH, ufw, fail2ban, Docker, unattended-upgrades.
- С 22 по 28 ноября прод **заморожен**, деплой только хотфиксов. Внешний uptime-пингер раз в 5 мин шлёт алерты в Telegram команды.
